# 运维与灾备（Operations）

> **文档性质：informative（不构成合规等级）**。
> 本文件**不新增 L5**，也不进入 `docs/CONFORMANCE.md` 的等级判定（ADR-0012 §4.2 #39 裁决）。
> 文中「建议/应」是运维实践建议，不是可用 `e2e-runner` 验收的契约 MUST。

## 1. 备份范围（分层）

| 层 | 内容 | 说明 |
|----|------|------|
| 业务数据 | 各扩展对象表（含双时间轴历史版本） | 恢复后必须保持 append-only 与版本链 |
| 事件存储 | 事件表 / 事件归档 | 与业务数据同一恢复点；outbox 不是事件历史（OBX-009） |
| 审计链 | `audit_entry` 全量 + **链头锚** | 链与锚必须同一恢复点，否则无法证明未截断 |
| 配置/密钥 | 字段散列密钥环（`EIS_FIELD_HASH_KEYS`）、授权夹具/角色数据 | 密钥丢失会导致写入专用字段不可复算（DRV-002/005） |

建议：业务表、事件、审计链、链头锚在同一备份集/同一快照点导出；跨库时保证同一恢复点。

## 2. 恢复后必做校验

1. **审计链自洽**：`python3 tools/audit-verifier <导出链> --json`（或 `05-audit-contract/verify.tool`）；
2. **链头锚比对**：恢复后的链头 hash 必须等于备份时的锚；不一致 → 停止上线、升级事件；
3. **事件摘要**：有事件导出时用 `audit-verifier --events` 复算 `payload_digest`；
4. **业务一致性抽查**：当前版本唯一（每 id 一条 `superseded_at IS NULL`）、余额/库存可重算；
5. **时间轴**：抽检 `as_of`/`recorded_as_of` 与版本历史相接无重叠（T-R009 约束在库层已强制）。

**禁止**：恢复后「重签/重算」审计链、删除审计条目、把锚表回滚到更早时点后再补写。

## 4. 恢复流程（建议）

1. 冻结写入（或切只读）→ 记录冻结时点与链头锚；
2. 按恢复点还原业务表、事件、审计链、锚、密钥环配置；
3. 跑 §2 的 1–4 项校验；任何一项失败 → 不解除只读；
4. 解除只读前做一次「写 → 读 → 审计」冒烟（`kind: scenario` 或人工命令）；
5. 记录恢复报告（恢复点、锚比对结果、校验命令输出、审批人）。

## 5. 明确不做

- 不新增 L5 合规等级（RPO/RTO 无法用 `e2e-runner` 验证）；
- 不规定备份产品、存储介质、异地策略、选主/切换算法；
- 不承诺「零数据丢失」；RPO/RTO 由部署方声明并演练；
- 不把本文件写成可自动验收的 MUST。

## 6. 可执行的部分

- 审计链/摘要校验：`tools/audit-verifier`（含冻结向量与 `--self-test`）；
- 恢复后业务冒烟：复用 `tools/e2e-runner` 场景或部署方集成测试；
- 链头锚比对：当前无内置工具（`docs/KNOWN-LIMITATIONS.md` §3.1/§3.2），需部署方实现并纳入演练。
