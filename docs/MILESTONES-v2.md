# EIS v2 里程碑计划（提案 / Draft）

> **状态**：提案，未生效。本文件不修改任何契约、不触发兼容性判定，只描述"如果要做，按什么顺序、做到什么算完"。
> **前置**：`00-invariants/` 与剖面（profile）等目标结构见同批整改报告（提案，未入库）。
> **口径**：以"周"为单位，不写日历日期（避免文档腐烂）。人力假设见 §8。

---

## 0. 总原则（三条，贯穿所有里程碑）

1. **每个里程碑必须留下三样东西**：一条可执行检查、一份可导出证据、一段 3 分钟可演示的录像脚本。三者缺一，不进入下一个里程碑。
2. **每个里程碑结束时必须回答 Gate 问题**，答不上就退回本里程碑，不许"边做边补"。
3. **不做无检查的规则**：任何新增 MUST 若无对应反例夹具，视为未交付。

## 1. 一页总览

| 里程碑 | 周期 | 主题 | 硬门（Gate） | 对外可展示物 |
|---|---|---|---|---|
| **M0** | 2 周 | 裁决与基线 | 6 份 ADR 定稿 + 基线数字有出处 | "我们量过现状"的一页数据 |
| **M1** | 3 周 | 不变式脊柱 | `invariant-checker` 全绿；每条有检查 | 一页不变式表（客户可读） |
| **M2** | 4 周 | 属主 + 引用快照 | 非属主写被拒；目标改名后历史重建一致 | "物料改名，三年前单据打印不变" |
| **M3** | 5 周 | 期间 + 更正 + 重建 | 锁定后记账被拒；聚合重建差异 = 0 | "关账后改错账，影响面全列出来" |
| **M4** | 5 周 | 剖面第一版（material） | `profile-checker` 过；物料合并/停用约束生效 | "库存没装，物料照样能用" |
| **M5** | 5 周 | 证据链 | 篡改样本全失败；外部 CLI 独立验证成功 | "这份审计包你可以自己验" |
| **M6** | 6 周 | 工具箱（DSL + 生成器） | 新对象 < 1 小时；生成物零差异 | "半天的工作变成十分钟" |
| **M7** | 6 周 | 可交付（最小 ERP + 客户文件） | 5 场景全绿；p99 达标；附件可投标 | 一份能进标书的技术附件 |
| **M8** | 持续 8 周+ | 采用与生态 | 首个真实业务验收签字 | 客户签字页 |

**累计**：M0–M7 共 **36 周**（约 9 个月），M8 与之部分并行并向后延伸。

## 2. 依赖关系

```
M0 裁决+基线
 └─► M1 不变式脊柱
      ├─► M2 属主+引用快照 ──┬─► M4 剖面(material) ──┐
      │                      │                        │
      └─► M3 期间+更正+重建 ─┴────────────────────────┼─► M7 可交付 ─► M8 采用
                                                       │
                             M5 证据链 ◄───────────────┤
                             M6 工具箱 ◄───────────────┘
```

- **关键路径**：M0 → M1 → M2 → M3 → M4 → M7。任何一格延期，交付线整体顺延。
- **可并行**：M5（证据链）与 M6（工具箱）不阻塞 M2–M4，可与 M3/M4 并行开工，但**不可早于 M2**（引用/属主语义未定，证据字段会返工）。
- **不可并行**：M1 与 M0。M0 的裁决决定 M1 的条目归属，跳过会导致脊柱重写。

## 3. 贯穿性质量门

| 门 | 触发 | 内容 | 失败后果 |
|---|---|---|---|
| **G1 检查门** | 每次 PR | `contract-checker` / `profile-checker` / `invariant-checker` / `temporal-checker` | 阻止合并 |
| **G2 生成物一致门** | 每次 PR（M6 之后） | 生成物与 DSL 零差异，禁止手改生成物 | 阻止合并 |
| **G3 场景门** | 每次 PR | 全部场景 + 反例夹具 | 阻止合并 |
| **G4 证据门** | 每次 PR（M5 之后） | 证据包可被独立验证器验证；篡改样本必须失败 | 阻止合并 |
| **G5 基准门** | 每次 PR（M7 之后） | p99 不劣于 `thresholds.yaml` | 警告 → 阻止（连续两次）|
| **G6 文档门** | 规则类 PR | 三件套齐备（损失场景 / 检查 / 证据） | 阻止合并 |

## 4. 里程碑详情

### M0 · 裁决与基线（2 周）

**目标**：把"要不要做"变成"按哪个决定做"，并量出现状基线，避免后续所有里程碑拿感觉当证据。

**客户价值**：无直接交付物，但决定后续 34 周是否白干。基线数据是日后"我们真的变快了"的唯一对照。

**范围**
- 做：6 份 ADR；版本矩阵草案；基线采集。
- 不做：任何目录搬迁、任何规则文件。

**交付物**
| 文件 | 内容 |
|---|---|
| `90-adr/0026-profile-layer.md` | 引入剖面层（必需集 vs 可选扩展的判据） |
| `90-adr/0027-evidence-conformance.md` | 取消 L1–L4 自评，改为 EP-1/2/3 证据级 |
| `90-adr/0028-material-ownership.md` | `InventoryItem` 归属裁决（material 是核心、库存不是）与迁移方向 |
| `90-adr/0029-retire-runtime-contracts.md` | `im` / `scheduler` / `outbox` 退出契约面，降为参考实现 |
| `90-adr/0030-read-audit.md` | 读访问审计进入核心契约（含必记字段与失败策略） |
| `90-adr/0031-naming-and-terms.md` | 命名纪律；`mgr`（management / 管理）等术语定稿 |
| `SPEC-VERSION.yaml`（草案） | core / profile / extension / kit 四类版本与冻结状态 |
| `docs/BASELINE-METRICS.md` | 基线：新增对象耗时、场景数、用例数、工具耗时、可复现的现状缺陷清单 |

**工作分解**
| 任务 | 估时 | 角色 |
|---|---|---|
| 6 份 ADR 起草（每份含"被否选项 + 失效条件"） | 5 d | 架构 |

| 基线测量（脚本化：新增对象计时、场景耗时、工具耗时） | 3 d | 工具 |

**验收**
```bash

```
基线报告须含至少 4 个可复算数字，且给出采集脚本路径。

**演示**：一页基线表 —— "现在新增一个对象要 X 小时，跑一遍全量要 Y 秒"。

**Gate 问题**
1. 剖面层的判据能否用一句话判定，且反例（不该进剖面的东西）说得清？
2. `InventoryItem` 是破坏性迁移还是别名过渡，选哪个、理由是什么、谁来承担迁移？
3. 读审计若默认 fail-closed，谁的系统会被打挂？开关由谁持有、如何留痕？
4. 取消 L1–L4 之后，已有对外合规声明怎么处理（重出证据 / 限期 / 并存）？

### M1 · 不变式脊柱（3 周）

**目标**：让"客户会损失什么"成为规范的顶层结构，取代按机制分类；每条不变式都挂上检查与证据字段。

**客户价值**：采购/审计第一次能读懂这份规范；合同附件有了编号体系。

**范围**
- 做：11 条不变式、失败模式库、v1 映射、检查器骨架、清单与兼容层。
- 不做：任何语义细节的最终定稿（属主/引用/期间的规则文本留到 M2/M3，M1 只定义条目与检查接口）。

**交付物**
| 文件 | 内容 |
|---|---|

| `00-invariants/inv-01..11-*.md` | 11 份展开文档（含反例与误用） |
| `00-invariants/failure-modes.yaml` | 机器可读失败模式库（供生成合同附件与风险评估） |
| `00-invariants/mapping-v1.md` | v1 六类契约 ↔ v2 双向映射与迁移备注 |
| `00-invariants/tests/invariant-negative.test.yaml` | 每条至少一条反例（可先声明为期望失败） |
| `00-invariants/tests/invariant-links.test.py` | 不变式 ↔ 规则 ↔ 检查 ↔ 场景 的引用闭合校验 |

**工作分解**
| 任务 | 估时 | 角色 |
|---|---|---|
| 11 条不变式撰写（每条含损失场景量化） | 6 d | 架构 |

**Gate 问题**
1. 有没有哪条不变式无法量化损失？若有，是降级为实践，还是删掉？
2. 每条不变式的检查命令现在都能跑吗？跑不了的是"明确失败"还是"假装通过"？
3. v1 的每条规则都能查到 v2 归属吗？有没有悄悄丢掉的约束？

### M5 · 证据链（5 周）

**目标**：把"我们说合规"换成"你可以自己验"。

**客户价值**：审计包可从供应商手里拿走、由客户或第三方独立验证——这是投标与合规评审最硬的一张牌。

**范围**
- 做：读审计规则族、证据包规范、规范形式、独立验证器、四套模板、负向门禁。
- 不做：法定时间戳服务集成（给接口不实现）；跨组织联邦验证。

**交付物**
| 文件 | 内容 |
|---|---|
| `10-core/audit/read-audit.rules.yaml` | RDA-001..012（必记字段含 `as_of` 与命中版本、失败策略、gap 标记） |
| `10-core/audit/hash-chain.spec.md`（扩展） | 新增条目类型（读 / 授权判定 / 更正说明书） |
| `60-evidence/evidence-pack.spec.md` | 包结构、条目类型、命名、最小化、保留期、分卷 |
| `60-evidence/canonical-form.md` | 唯一哈希口径 + 冻结测试向量 |
| `tools/eis-verify` | 零依赖 CLI：包 + 公钥 → 通过/失败 + 差异定位 |
| `60-evidence/templates/*.md` | 合同附件 / 验收报告 / 更正说明书 / 审计附件 |
| `60-evidence/tests/pack-{valid,tampered,expired,unsigned}.json` | 正例 + 三类反例 |
| `.github/workflows/evidence.yml` | 篡改样本必须失败（负向门禁） |

**工作分解**
| 任务 | 估时 | 角色 |
|---|---|---|
| 读审计规则与条目类型设计 | 4 d | 架构 |
| 规范形式与测试向量 | 4 d | 工具 |
| 证据包规范 + 导出实现 | 5 d | 工具 |
| 独立验证器（零依赖） | 5 d | 工具 |
| 四套模板 | 3 d | 文档 |
| 负向门禁与样本 | 2 d | 工具 |

**验收**
```bash
tools/eis-verify --pack 60-evidence/tests/pack-valid.json --pubkey fixtures/pub.pem      # 通过
tools/eis-verify --pack 60-evidence/tests/pack-tampered.json --pubkey fixtures/pub.pem   # 必须失败
```

**演示**：把一份审计包交给一个不懂系统的人，用一条命令验证，并指出被篡改的那一条。

**Gate 问题**
1. 读审计默认 fail-closed 会不会把高并发读打挂？开关如何授权、如何留痕、gap 如何计入证据？
2. 规范形式冻结后还能改吗？不能改的部分与可扩展的部分怎么分？
3. 验证器零依赖的边界在哪（是否允许调用系统 `openssl`）？

### M6 · 工具箱：DSL + 生成器（6 周）

**目标**：让规范能生成工件，把"新增一个业务对象"从半天压到十分钟。

**客户价值**：交付毛利；也是防止实现与规范漂移的唯一机械手段。

**范围**
- 做：schema DSL（对象/字段/属主/唯一键/引用/状态机/期间/权限/租户字段）；生成 DDL、迁移 diff、OpenAPI、Java/TS 类型、表单骨架、夹具；`temporal-checker`；租户字段规则族。
- 不做：可视化建模器；多语言全覆盖（只覆盖交付栈实际语言）；代码生成后的业务逻辑（只生成骨架）。

**交付物**
| 文件 | 内容 |
|---|---|
| `50-kit/schema-dsl/grammar.md` + `examples/` | DSL 语法与示例（含 material 的等价声明） |
| `50-kit/generator/eis-gen` | 生成器（子命令：ddl / migrate / openapi / java / ts / form / fixture） |
| `50-kit/generator/tests/` | 生成物快照测试 |
| `10-core/evolution/tenant-fields.rules.yaml` | TEN-001..012（声明式、类型白名单、演进语义） |
| `tools/tenant-field-checker` | 租户字段合法性与升级演练 |
| `tools/temporal-checker` | 扫描全部读截面，未显式声明时点即失败 |
| `.github/workflows/ci.yml`（扩展） | 生成物一致性门（禁止手改生成物） |

**工作分解**
| 任务 | 估时 | 角色 |
|---|---|---|
| DSL 设计与语法 | 5 d | 架构 + 工具 |
| 生成器内核（模板 + diff） | 10 d | 工具 |
| 各目标生成器（DDL/OpenAPI/Java/TS/表单/夹具） | 10 d | 工具 |
| 租户字段规则 + checker | 4 d | 架构 |

**验收**

**演示**：现场写 30 行 DSL，10 分钟得到可跑的 DDL + API + 前端表单 + 夹具。

**Gate 问题**
1. DSL 与现有 JSON Schema 的关系是什么（谁是权威）？
2. 生成物被手改怎么发现？发现后怎么处理（回灌 DSL 还是丢弃）？
3. 租户字段会不会变成"合法的核心修改"？边界在哪？

## 8. 人力与裁剪

**默认假设**：1 名语义架构 + 1 名工具/内核 + 0.5 文档交付 = 2.5 人，36 周。

**只有 1 人时**（删减顺序，从后往前）：
1. 砍 M6（DSL 与生成器）→ 保留 DSL 文档，生成器延期；代价：对象落地仍靠手写，交付毛利不达标。
2. 砍 M8 的 `asset` 与 `ai-guardrails` → 只留试点支持。
3. 砍 M7 的 `legacy-coexistence` 场景 → 代价：进不了存量客户市场。
4. **不可砍**：M0 / M1 / M2 / M3 / M5。理由：这五项构成"可自证"的最小闭环，少一项则价值主张不成立。

**只有 1.5 人（1 架构 + 0.5 工具）时**：M1–M5 照常，M6/M7 合并为 8 周，M8 取消，转为"外部采用者自助"。

## 9. Kill criteria（何时应当停下重估）

出现以下任一情况，暂停推进并重估方案（而不是继续加人）：

1. **M3 结束时**仍无法演示"三个月前的错误更正并重算差异 0"——说明期间/更正语义设计有结构性错误。
2. **M5 结束时**独立验证器无法在未知实现上跑通（只能验自己导出的包）——说明规范形式没有真正统一。
3. **M6 结束时**新增对象仍需 > 4 小时——说明 DSL 抽象错了，生成器不如手写。
4. **M8 结束时**试点整改条目 > 10 条且集中于语义类（而非实现类）——说明规范本身有洞，而非客户不配合。
5. 任一里程碑连续两次 Gate 未通过。

---

## 10. 变更控制

- 里程碑周期变更：任何 ±1 周以上调整，须在里程碑开始时提出，并说明被压缩的验收项。
- 范围变更：新增交付物必须回答"它服务哪条不变式 / 哪个客户损失场景"，否则进"以后再说"清单。
- Gate 记录：每次 Gate 结论写入 `docs/MILESTONE-LOG.md`（本计划不含该文件，由 M0 建立）。
- 每两周一次 30 分钟同步：只看三件事——Gate 风险、kill criteria、被砍掉的东西。
